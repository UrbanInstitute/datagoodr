Data-Type Detector Guide

What this is

datagoodr ships a library of data-type detectors: small functions that answer one yes/no question about a column of values — “is each value an X?” — where X is a semantic type such as an email address, an ISO currency code, a census tract GEOID, or an ORCID iD. Each detector is a pure predicate:

  • input: a character vector x
  • output: a logical vector the same length as x (TRUE where the value matches the type, NA where x is NA); detectors never error.

The detectors are deliberately independent of the workflow that chooses among types (guess_data_type()), so each can be tuned in isolation. This guide is the catalog of what is implemented today, grouped by family, with a short definition, examples, the detection strategy, and a validation report for each type.

How the detectors are validated

Every type ships with a set of real positive examples. To measure whether a detector is not just permissive but precise, we also generate plausible-but-wrong negatives from those positives, using the mutation strategies from the AutoType paper (Yan & He, SIGMOD 2018), plus a structure-scramble strategy:

Tier Name What it changes Purpose
S1 preserve-structure replaces only alphanumeric characters, leaving punctuation/delimiters in place weakest negatives; for loosely-structured types it often regenerates valid values
S2 preserve-alphabet replaces any character, drawing only from the alphabet actually observed corrupts structure while staying “in vocabulary”
S3 random replaces characters with arbitrary printable ASCII strongest random negatives
SP scramble-structure keeps the alphanumeric characters and their order, but permutes the positions of punctuation/delimiters catches detectors that check “right characters present” but not “in the right place” (decimal point, grouping, symbol order)

The frozen mix of valid + labelled negatives is the bundled [data_type_tests] object. The report below applies each detector to that fixture and reports pass rates per tier:

  • Recall — share of real positives accepted. Should be 1.00.
  • S1 / S2 / S3 / SP — share of generated negatives wrongly accepted (a false-positive rate). Lower is better; blank means that tier produced no distinct negatives for the type.

One caveat to read the numbers correctly: a high S1 is expected and not a bug for loosely-structured types. Mutating only the digits of "$12.30" yields "$47.99" — still a valid amount — so S1 measures little there. The discriminating tiers for such types are S2/S3/SP.

Adding a new detector

New types are added with a copy-paste, bring-your-own-LLM workflow — no API key required. Collect 10-25 example values of the new type and call [draft_detector_prompt()]. It builds the AutoType test cases for your examples and assembles a self-contained prompt (a versioned contract + your positives + generated hard negatives) that you paste into any LLM:

draft_detector_prompt(
  examples  = c("ENSG00000139618", "ENSMUSG00000102659", "ENST00000407559"),
  type_name = "ensembl_id"
)

The prompt is printed to the console and written to a .md file you can attach to a chat. When the LLM returns an is_<type>() function, score it with [evaluate_detector()], which runs the same recall/precision report used above so you can see how it performs before adopting it. Once you are happy, drop the function into an R/dt-<family>.R file, add its positive examples to data-raw/datatypes/<family>.R, and register one line in R/00-data-type-registry.R.

See ?draft_detector_prompt and ?evaluate_detector for details.
